# Restricted Linux execution

Version 0.7.0 adds cooperative resource-pool admission to the separate Git preparer and allocation/inode limits. The Docker containment policy remains `linux-container-v3`. It runs deterministic fake-agent actions and post-run checks against trusted local fixtures. It does not approve hostile repositories, real adapters, paid-model calls, or production credentials. The acceptance tests use disposable test-only credential values.

## Execution boundary

Local execution validates task v1 and resolves the exact commit with sanitized host Git plumbing. It checks the tree and sizes before materialization, initializes private bare metadata with an empty template, borrows source objects through a read-only alternate, and creates a detached worktree with `--no-checkout`. Batched raw blob reads verify object hashes and lengths before writing files. Private attributes disable filters and checkout conversions; hooks, fsmonitor, inherited Git configuration/environment, network protocols, and lazy fetch are disabled. Source Git configuration is not copied into the private repository, and captured blobs/indexes never enter the source repository. Git still parses the trusted source's metadata and objects. See [raw object reads](https://git-scm.com/docs/git-cat-file), [object alternates](https://git-scm.com/docs/gitrepository-layout), and [attribute precedence](https://git-scm.com/docs/gitattributes).

Docker execution never invokes host Git. The controller locates only real standalone SHA-1 object directories, copies bounded opaque loose objects and pack/index files, and rejects nonempty external alternates, links, linked-worktree metadata, and unsupported entries. It copies no source config, hooks, refs, or working files. Snapshot limits are 256 MiB total, 128 MiB per compressed file, and 20000 traversal entries. A manifest hashes each copied file and the ordered snapshot identity. The source is not mounted into any container.

The fixed preparer image is official Node 24.20.0 Bookworm, `node@sha256:9137a20e25879e0b557227b57e3ee4e9af4bde29eb3db66134cd1723e84f830b`, with Git 2.39.5. Only the copied object snapshot and bundled runner worker mount read-only at `/input` in the preparer. The agent never receives either. The preparer initializes minimal private Git metadata with controlled alternates to that snapshot, applies the same sanitized raw-blob operations as local execution, and returns validated files. Private Git parsing, tree/blob reads, index construction, and binary diff generation all occur there.

`pnpm build` bundles the TypeScript worker and dependencies with esbuild. No packages install at runtime. Preparation request/response v1 are discriminated unions with only prepare-at-exact-revision and patch operations, plus structured responses/errors. No task commands, environment additions, or arbitrary Git flags enter this protocol. Transport is capped at 96 MiB. The host validates versions, operation identity, resolved revision, paths, modes, base64, aggregate limits, and file digests before accepting files. These digests identify bytes, not authenticated proof that a compromised image/parser reported truthful evidence.

Docker requires a non-root Linux runner and a trusted local Engine at `/var/run/docker.sock`. The runner ignores Docker contexts and uses an empty per-attempt Docker configuration directory. It never mounts the engine socket or configuration into the container. Only a preinstalled `repository@sha256:<digest>` image is accepted; there are no implicit pulls. Images must provide `/usr/local/bin/node` version 22 or newer and must not declare volumes.

The fixed `linux-container-v3` agent policy is:

| Setting         | Value                                                                                          |
| --------------- | ---------------------------------------------------------------------------------------------- |
| Network         | `none`, loopback only, no published ports                                                      |
| Writable files  | `/workspace` tmpfs volume: 128 MiB allocated blocks, 12000 inodes; `/tmp`: 64 MiB, 4096 inodes |
| Root filesystem | Read-only                                                                                      |
| User            | Runner's nonzero Linux UID and runner GID                                                      |
| Privileges      | All capabilities dropped, no new privileges, private IPC, engine-default seccomp               |
| Resources       | 512 MiB memory with no extra swap, 1 CPU quota, 128 PIDs                                       |
| Lifecycle       | Start for each action/check, kill the whole container afterward                                |
| Environment     | Image defaults and explicit task additions, no inherited host environment                      |

The preparer uses the same fixed privilege, network, CPU/PID, read-only-root, and temporary-filesystem restrictions. Its memory limit is 768 MiB and private `/workspace` allocation is 256 MiB/40000 inodes. Separate read-only holders keep the agent workspace and preparer Git state mounted. Both holders execute only fixed runner code; the preparer holder has no input mount. All resolved mount/resource/image settings and mounted quotas are checked before use. Source Git config is never consulted; only the bounded copied objects are parsed. See [the official Node image source](https://github.com/nodejs/docker-node) for image provenance, which still needs security review.

## Storage decision

Ordinary Docker volumes do not impose a byte or inode quota. This backend uses the Linux local driver with `type=tmpfs`, `device=tmpfs`, and fixed `size`, `nr_inodes`, `uid`, `gid`, `mode=0700`, `nosuid`, and `nodev` options. It verifies those options and ownership labels, then verifies actual filesystem type, block capacity, and inode totals through Node `statfs`. Unsupported drivers/kernels/engines fail preparation, never fall back to a host directory. See [Docker's local tmpfs volume example](https://docs.docker.com/reference/cli/docker/volume/create/) and [the kernel's allocation/inode semantics](https://cdn.kernel.org/doc/html/latest/filesystems/tmpfs.html).

A separate non-root, offline, read-only-root holder mounts the workspace volume read-only with the same resource/privilege restrictions. Only fixed runner code executes there: a keeper and bounded export helpers. It never receives task commands, task environment additions, repository scripts, or host mounts. Preparation tests that holder writes fail with `EROFS`. The holder remains running while agent containers stop between commands, because unmounting tmpfs destroys its contents. Its original start timestamp is checked before execution/export; a lost or restarted holder cannot silently supply a reset workspace. The preparer follows the same lifecycle and whole-container termination after each worker operation.

Kernel limits apply to allocated blocks and inodes, not logical file lengths. Files, directories, and some extended attributes consume inodes. Sparse truncation can create huge logical lengths without allocating blocks; export rejects such files before reading them. The existing logical 64 MiB workspace/16 MiB file limits are intentionally stricter than the live allocation limit. The 128 MiB live limit allows block rounding for small files and intermediate command writes, not a larger capture allowance. `/tmp` uses explicit inode limits as well as bytes, and resets on every agent restart. Other virtual device/proc/IPC mounts remain part of Docker's standard setup; these workspace quotas are not a claim that every virtual filesystem has this inode policy.

Export runs through the read-only holder only after the agent is quiescent. Fixed helpers stream directory iteration, refuse links/special files, use bounded descriptor reads, and return base64 regular files under fixed logical limits. The JSON transport is capped at 96 MiB. The host validates the payload, paths, modes, base64, aggregate bytes, entries, and metadata before exclusive file creation. It never unpacks tar from the daemon or copies a sparse logical length unchecked. Invalid entries leave a bounded partial export and available artifacts; the patch remains explicitly uncaptured. The complete raw agent volume remains mounted for inspection if export is incomplete. Incomplete Git capture also retains the preparer's separate private volume; copied source inputs and available host snapshots remain recorded. Later checks can change that retained raw volume; the partial host export records the capture point.

Successful export permits holder/volume removal after checks. Incomplete export retains both, records their generated names/ID and `storage.cleanup=retained`, and still removes the agent container. Ownership is revalidated before any resource removal. Retained holders consume bounded RAM/swap. Opt-in pools limit recorded admission charges, but there is no host-wide retained-resource quota or automatic cleanup/recovery. Inspect only recorded names and labels; save needed evidence before removing their last mount. A daemon restart, host reboot, or holder failure may lose raw tmpfs contents. `--keep-worktree` retains a complete host export, not a live volume after successful export.

Docker's virtual device, proc, and private IPC mounts still exist; read-only root does not make every virtual filesystem read-only. Tasks cannot override these settings or add mounts, networks, ports, capabilities, or Docker options. There is no credential broker or provider network grant yet. Digest pinning identifies bytes, not image trust or provenance. Docker documents [network-none behavior](https://docs.docker.com/engine/network/drivers/none/), [runtime restrictions](https://docs.docker.com/engine/containers/run/), and [the host/daemon trust boundary](https://docs.docker.com/engine/security/).

## Admission accounting decision

An opt-in pool owns bounded copied inputs, host snapshots/exports, controller directories, and canonical results for Docker attempts. Policy, ledger, inventory, and admission decisions are versioned v1 JSON contracts. Local execution is not managed by this profile. A pool is new and explicit; it does not adopt prior evidence or discover unrelated Docker resources.

Admission checks the fixed planned reservation against all recorded active/completed/retained charges under an exclusive on-disk lock. It records names before resource creation, then creates an owned attempt directory and temporary parent. Cooperating processes cannot pass the same capacity check concurrently. A busy/stale lock is refused, never broken automatically. Exited PIDs and missing containers are not grounds for silent reclamation. Unfinished records retain their full reservation across restart.

Each attempt reserves 768 MiB of logical pool files, 60000 entries, 384 MiB of agent/preparer volume allocation, four containers, two volumes, and one lifetime record. Metadata/atomic-write overhead separately charges 20 MiB/32 entries; ledgers are capped at 8 MiB and 1000 records. Managed tasks have 1 MiB/1000-action/1000-check limits and a conservative output preflight. Canonical result writes cap serialized bytes at 128 MiB. Managed commands also cap redacted persisted streams without splitting UTF-8, mark truncation, and retain digests for bounded raw capture and persisted text. Raw truncated bytes beyond capture are not represented by those digests.

The canonical result is saved before checkout removal. Caller result/batch mirrors must remain outside the pool, including through aliases; they are not charged. Complete cleanup releases recorded Docker charges and keeps measured logical file charges plus the lifetime record. Retained or ambiguous attempts keep conservative capacity. Unknown measurement, altered ownership, undercharging, unregistered entries, or changed finalized bytes refuse admission. Measurements are bounded and refuse links/special files; filesystem races remain outside this guarantee.

Inventory reads registered state only, do not persist changes, and do not probe/remove Docker resources. Saved cleanup statuses/IDs are observations, not live ownership attestation. No retry, lease expiration, lock breaking, evidence reclamation, repair, or resume is implicit. A refusal starts no adapter and emits decision v1; batch index v2 marks admission refusal as `not_started/resource_admission` instead of persistence failure.

This is accounting for cooperating runners sharing one pool, not a hard host filesystem quota, physical-space preallocation, global RAM limit, or host-wide resource discovery. Block rounding, image storage, caller mirrors, other pools, unrelated writers, concurrent mutation, power loss, and kernel/daemon failure remain outside it. Actual `ENOSPC` can still prevent final evidence. Hard Linux filesystem quotas and aggregate host enforcement remain required security work.

## Lifecycle and evidence

1. Copy bounded opaque objects, create/verify the fixed preparer and its quota volume/holder, and resolve/materialize the revision through the worker. Validate returned files on the host, then create/verify the separate agent volume/holder/container and import files. The preparation phase has a 30-second deadline.
2. Route fake file writes and agent commands into that container. The runner owns the wall-clock and command budgets. File-write helpers do not count as agent commands.
3. Kill and inspect the agent container after every command, even if its parent process exited successfully. Restarting clears `/tmp` and descendants; only workspace files carry over through the holder. A stop failure refuses further commands and capture that requires a stopped workspace.
4. Once quiescent, export through the read-only holder under the entry, depth, per-file, total-byte, and transport limits. Reject symlinks, hard links, special files, metadata paths, and nonportable names. Materialize only validated files with exclusive writes. Send bounded files to the restarted preparer, build its private raw index, and validate the returned patch. Capture patch/artifacts before checks under a separate 30-second deadline. Patches include ignored regular files and disable external diff, textconv, and rename detection. Oversized patches are rejected, never truncated.
5. Run checks under the same restrictions, with their own deadlines. Check writes do not enter the already-captured agent patch or artifacts.
6. Remove only the current attempt's agent and preparer process containers and, after their respective complete captures, their holders/volumes. Persist an evidence snapshot, then remove disposable directories. Capture/cleanup failure, initial persistence failure, or `--keep-worktree` retains host workspace evidence. Incomplete export also retains raw holder/volume evidence. Agent containers are removed even when evidence is retained.

Result v7 records agent/preparation image/runtime/policy/cleanup evidence and admitted accounting mode/policy/reservation. Preparation also records Git version, worker digest, copied object snapshot digest/bytes/files, and retained input path. Unavailable fields remain null. Failed preparation retains copied inputs and starts no adapter. Incomplete capture retains the relevant raw volumes and host snapshots. Comparison v6 preserves this evidence while excluding generated container/holder/volume/path identities from stable-runtime comparisons. Worker bytes and preparation Git/Node/Engine identity are compared.

Execution/storage policy, fixed preparer image/policy, requested agent image, safety policy, and accounting mode/limits enter shared-task identity. Generated pool/reservation IDs and pool paths do not. Result v1-v6, comparison v1-v5, and batch index v1 remain archived and unchanged. Scoring stays v2. Current comparisons reject older results/indexes rather than infer accounting identity; there is no migration.

## Limits that still matter

- Local execution still trusts host Git and host filesystem/network authority. Docker uses only copied objects, but copying remains non-atomic against concurrent host mutation and filesystem races. Committed or unreachable objects may contain secrets. Host path discovery and bounded filesystem APIs remain trusted; this change contains Git parsers, not hostile host users or kernel filesystem calls.
- Docker shares the host kernel. Kernel/runtime vulnerabilities, a compromised daemon, a malicious image, or a hostile host user are outside this boundary. Docker socket access gives the host controller substantial authority. There is no VM isolation or cross-platform equivalent.
- Memory/CPU/PID settings constrain container processes, not runner work. Live tmpfs allocation/inode limits constrain agent/check workspace writes, and capture separately bounds logical bytes, file sizes, entries/depth, metadata, patches, and artifacts. Copied object snapshots, validated host files, local private Git objects, exports, and saved results have no hard host filesystem quota. Docker private Git state is quota-limited in the preparer. Local execution is unquotaed, and repeated retained holders/exports can exhaust aggregate host memory, swap, or disk outside the cooperating pool accounting. Tmpfs may use host swap; it is not encrypted secret storage or fsync-backed persistence.
- The agent deadline covers actions and command startup. Preparation/capture have separate deadlines, Git subprocesses have kill-on-timeout/cancellation, and filesystem loops checkpoint between operations. These cannot preempt stalled kernel calls, synchronous hashing/compression, or races with a hostile host user. Docker metadata/cleanup requests have individual 10-second limits; command startup/import/export use the remaining execution/phase deadline. Termination/cleanup can exceed deadlines; a stuck daemon can prevent cleanup. There is no total run/batch deadline.
- `SIGKILL`, power loss, and storage/daemon failure can leave containers, volumes, exports, or the last snapshot, and can lose raw tmpfs bytes. Inspect recorded owned resource identities and retained paths. There is no automatic recovery or resume.
- Redaction is a text backstop. Encoded, unknown, short, binary, or repository-committed credentials can escape it. Image environment defaults and task additions must already be trusted.
- The preparer image pins its Git/Node bytes, not the host kernel, Engine, hardware, filesystem behavior, or scheduling. Local execution still uses an unpinned host Git/toolchain. Arbitrary commands remain potentially nondeterministic. Saved reports regenerate byte-identically; independent runs do not.

For these reasons, this backend remains limited to trusted repositories and commands. Stronger isolation must precede permission to run untrusted inputs.

## Verification and next gates

The README provides the exact image pull and `pnpm example:isolated` commands. The acceptance script creates trusted temporary repositories and verifies failed host reads/writes, denied host-service connections, no inherited test credential or Git/Docker metadata, non-root/capability restrictions, detached-child termination, time/command budgets, preparation/agent cancellation, redaction, evidence capture/scoring, actual workspace/temporary byte and inode `ENOSPC`, failed-command evidence with later checks, host-Git-blocked packed checkout and binary patch replay, inert source configuration, rejected alternates/malformed objects, rejected symlink and oversized exports, forensic holder/volume retention, successful cleanup, repeated workspaces, managed cancellation/cleanup/retention, built resource CLI initialization/inventory, refusal without evidence changes, and deterministic saved-report regeneration. It preserves results locally and never uploads them. Failed/rejected fixtures retain copied inputs and their generated source repositories for inspection; preparer metadata depends on the copied snapshot, not the original source. Focused Git/workspace/storage/preparation tests cover filters/hooks/ambient config, binary patch replay, unsupported entries, traversal/read limits, aggregate artifact caps, phase deadlines, weakened quotas, escaping export paths, and malformed export bytes. These targeted probes are not an adversarial security audit.

To verify the acceptance script without the `tsx` loader on Linux, run `pnpm exec tsc -p tsconfig.isolation.json`, then `node .agent-eval/isolation-tools/scripts/run-isolated-example.js`. This also supports a Windows checkout accessed from WSL, provided Node.js 22 or newer and Docker run inside Linux. Run the normal build first when checking the CLI.

Before a real adapter:

- Protect host snapshot copying against concurrent mutation, and enforce real host filesystem/aggregate resource quotas beyond cooperative admission. Protect preparation/export from concurrent filesystem mutation.
- Review the threat model and image provenance, and add adversarial escape tests or VM isolation as required.
- Design a credential broker and controlled provider egress that cannot reach host/private services.
- Collect trustworthy provider usage and enforce token/cost budgets outside the provider process.
- Define adapter capabilities and toolchain identity without weakening the fixed backend silently.

Resume and a small versioned evaluation suite follow as separate roadmap work. No first-provider choice is implied by this implementation.
